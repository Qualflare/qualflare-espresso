# Device spike, 2026-09-20 — measured, not assumed

Run: `Android spike` workflow, six legs (API 24 / 29 / 34 × plain / orchestrator), all green.
Maestro of this exercise: answer the three questions that decide the reporter's shape *before* writing
it. All three are answered, and one answer changed the plan.

## 1. The report reaches the host with no `adb pull` — on API 29+ only

On API 29 and 34, both plain and with Android Test Orchestrator, a file written through
`PlatformTestStorageRegistry.getInstance().openOutputFile(name)` arrives on the host by itself:

```
fixture-app/build/outputs/connected_android_test_additional_output/debugAndroidTest/connected/emulator-5554 - 14/qualflare-spike-api34.json
  {"spike":true,"api":34}
fixture-app/build/outputs/connected_android_test_additional_output/debugAndroidTest/connected/emulator-5554 - 14/qf-attach-spike.txt
  second stream from the same sink
```

Two things follow. The install story holds — one Gradle line and `qf collect`, no adb. And **a report
and its screenshots can share one sink**, so a `localImagePath` written as a bare filename will resolve
next to the report.

**On API 24 nothing is pulled.** The cause is visible in the log rather than guessed:

| Leg | `additionalTestOutputDir` instrumentation argument | pulled to host |
|---|---|---|
| API 24 plain | `null` | no |
| API 24 orchestrator | `null` | no |
| API 29 plain / orchestrator | `/sdcard/Android/media/<pkg>/additional_test_output` | yes |
| API 34 plain / orchestrator | `/sdcard/Android/media/<pkg>/additional_test_output` | yes |

AGP simply does not pass the argument below API 29, so `FileTestStorage` writes to an on-device default
that Gradle never collects. This is a platform boundary, not something the library can fix.

**Decision: minSdk stays 24 and the boundary is documented.** On API 24–28 the reporter falls back to
the app's files directory and prints the exact `adb pull` command; on 29+ it is automatic. Raising minSdk
to 29 would have bought one story instead of two, at the cost of excluding a real slice of Android
estates.

## 2. The `listener` instrumentation argument works

```
SPIKE listener testRunStarted, tests=2, thread=Instr: androidx.test.runner.AndroidJUnitRunner
```

One line in the consumer's `build.gradle.kts`, no per-class annotation, and it fires on every leg. The
storage implementation resolved is `androidx.test.platform.io.FileTestStorage`.

This validates choosing the listener argument over shipping an `AndroidJUnitRunner` subclass: the
argument composes with whatever runner the consumer already has (Hilt's, for instance).

## 3. `testFailure` arrives *after* `@After` teardown

```
SPIKE [failsAfterTeardown] about to fail with the activity still open
SPIKE [failsAfterTeardown] @After running and closing the activity
SPIKE [failsAfterTeardown] @After finished; a listener's testFailure has NOT been called yet
SPIKE listener testFailure failsAfterTeardown isSuite=false exception=java.lang.AssertionError
```

`RunAfters` runs `@After` and *then* throws, so by the time the listener hears about a failure the
activity is gone. **Screenshot-on-failure cannot live in the listener**; it has to be a `TestWatcher`
rule declared inside the activity rule, so that it runs before teardown.

## 4. Bonus: the main-looper hazard is real

```
SPIKE [failsAfterTeardown] onActivity thread = main
SPIKE [failsAfterTeardown] test thread = Instr: androidx.test.runner.AndroidJUnitRunner
```

`ActivityScenario.onActivity{}` runs on the **main looper**, not the test thread. A `ThreadLocal`
holding the "current case" would silently drop every `Qualflare.step()` or `Qualflare.label()` call made
from inside `onActivity{}` or a `ViewAction` — exactly the calls a test author is most likely to write.
The current case must be a single `static volatile`, which is safe because `AndroidJUnitRunner` runs
tests serially.

## What this changes in the plan

- `ReportSink` (task 6) is not "storage, with a rare fallback". The fallback is the **normal** path on
  API 24–28 and must be as well tested as the primary one, including the printed `adb pull` line.
- `docs/LIMITATIONS.md` gets the API-29 boundary as a measured fact, with the argument value as evidence.
- Task 11's screenshot capture is a `TestWatcher` from the start; there is no listener-based variant to
  try first.
- Orchestrator made no difference to delivery on any API level. The remaining orchestrator question —
  one report file per test, and whether `qf collect` merges them — needs the real reporter and stays open
  for task 13.
